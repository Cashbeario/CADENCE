Cadence: what happens behind the scenes

A walk through the code as it stands today: what the model is actually sent, what the daemon does while you are away, where memories, ideas and goals come from, and what each extension point (skills, hooks, plugins, MCP) really does. The last section lists the problems I found while reading it.

1. The big picture

One Python process (cadence web) holds everything. It serves the web app, keeps live chat sessions, and runs a daemon loop in the background. All state lives as plain files under ~/.cadence/state (JSON and JSONL), plus a vector index in Qdrant for memory search. All model calls go to one OpenAI-compatible server (LM Studio here).

Two models, two jobs

big does the agent loop, planning, task reflection and brainstorming. small does housekeeping: compaction summaries, distilling tool output, lesson consolidation and the new post-turn reflection. Right now both point at ornith-1.5-35b-a3b, so "small" work competes with "big" work on the same server.

Three ways work starts

(1) You send a chat message. (2) You or an idea create a task, and the daemon runs it. (3) A goal exists and the planner queues tasks for it. Chat is interactive; tasks and goals are autonomous.

Everything is project-scoped

A project is a folder. Its file tools, shell, skills, instructions, canvas, browser, goals, tasks and ideas are tied to that folder. Memory is scoped too: each memory belongs to a project, or is marked shared.

2. When you send a message

  1. Browser → server. The web app sends {op:"send", session, text, images, files} over the WebSocket. If files were attached, they were already uploaded; they get copied into the project and their extracted text is appended to your message (see §9).
  2. Session loaded. The server finds the live session or reloads it from ~/.cadence/state/sessions/<id>.json. If a turn is already running, your text becomes a steer: it is injected before the agent's next model call instead of starting a new turn.
  3. Hooks: session_start, then user_prompt. A hook can block the prompt, or print text that gets appended to your message as "[context from hooks]".
  4. Memory recall. Your message is embedded and searched against memory (top 5, vector and keyword blended). The hits are stored on the agent and placed in the system prompt. This happens once per user message, not on every loop iteration.
  5. The loop starts (max 40 iterations). Each iteration: apply any steering; rebuild the system prompt; compact if the window is too full; send everything to the big model and stream the reply.
  6. Streaming to the UI. Text tokens, "thinking" tokens and (new) the arguments of a canvas_write call are forwarded live, so a document appears in the canvas while it is being written.
  7. Tool calls. For each call: pre_tool hooks (can block), run the tool with a 120 s timeout, post_tool hooks (can append text). Read-only tools in the same batch run in parallel. The result is truncated to 8,000 characters and added to the conversation. An identical call repeated 3 times gets a warning appended.
  8. Loop until no tool calls. When the model answers with plain text, the stop hook fires, the session is saved, and the final message is sent to the UI.
  9. After the turn (new). A background reflection pass reads the turn and files memories and ideas (§5). It runs after the UI already has the answer.

3. What is in the context window

Every model call is: one big system message, then the conversation, plus the tool definitions. In order:

Token counts are estimates (about 3.6 characters per token), used to decide when to compact. The window size used is big.context_window from config, which defaults to 32,768 unless you set it (see findings).

4. Compaction

Before each model call, the loop checks whether usage is above 70% of the window. If so it works down toward 40% in three escalating stages, stopping as soon as it is low enough. The most recent 8 messages are never touched, and a tool call is never separated from its result.

1 ShrinkNo model. Old tool outputs over ~2,000 chars keep only their head and tail.
→
2 DistillSmall model condenses each very large old tool output (≥1,800 chars) to the facts that matter, marked [distilled].
→
3 FoldSmall model merges the oldest messages, a few thousand tokens at a time, into the rolling summary (Goal, Decisions, Files touched, Commands, Errors, Open items).
→
EmergencyAbove 92% after all that: the summary is cut and the oldest turns are simply dropped.

If the small model fails, a deterministic summary (user asks and tool names only) is used instead. The UI shows a note each time compaction runs.

5. Memory: when is one created?

There are three kinds: episodic (what happened), semantic (facts), procedural (how-tos and rules). Exact-duplicate text is ignored. Memories are written to memory.jsonl and embedded into Qdrant lazily, the next time a search runs.

When memories are read: chat recall (top 5 on each user message), the agent's memory_search tool, the planner (last 6 procedural), and brainstorming (last 8 procedural). Ranking is a blend of vector similarity (floor 0.55) and keyword overlap, with a small recency bonus. If the embedding server is unreachable it silently falls back to keyword-only.

6. What the daemon is doing

The daemon is a loop that wakes every ≤30 seconds, or immediately when something calls wake() (a new task, a promoted idea, a goal change). It is separate from your chat; it never touches a chat session. Each pass:

  1. Launch ready tasks. Up to max_parallel_goals (2) pending tasks run concurrently, skipping tasks of paused goals or archived projects. Each gets its own fresh agent scoped to its project.
  2. Plan goals. Any active goal with no open tasks is planned (one planning call at a time). A goal that was just planned with nothing queued waits 10 minutes; a goal that has used its daily task budget (6) waits for tomorrow.
  3. Heartbeat cycle. Only when nothing else is running, and at most reflection_cycles (6) times a day, spaced 4 hours apart: one idea cycle (brainstorm for one project, rotating, projects with active goals first) and one improvement cycle (consolidate lessons into memory).

On startup, tasks left "active" by a crash go back to the queue. A pause switch stops launching and planning.

When a task ends, the task_done hook fires and, if it belonged to a goal, that goal is re-planned right away.

7. Ideas, brainstorm, goals and tasks

Idea

A cheap, unvetted inbox item. Nothing runs until you promote it, to a task (one verifiable change) or a goal (long-horizon). Sources: you, the daemon's idea cycle, and now post-turn reflection. Goal-sized ideas stay in the inbox until you promote them.

Brainstorm button

Calls the big model once with: a snapshot of the project's file tree (up to 80 files, 3 levels deep), the last 25 known idea/task/goal titles ("do not repeat"), and the last 8 procedural lessons. It asks for up to 3 ideas as JSON, drops near-duplicates (word overlap ≥ 0.6) and files them as ideas. The daemon's idea cycle uses the same function. With auto_approve_ideas on, task-sized ideas are promoted straight to tasks; yours is off.

Goal

A long-term objective with a vision, success criteria, a journal and a progress estimate. The planner (big model) reads the goal, its tasks so far, journal, lessons and project tree, then replies with an assessment, a progress number, a status (working / achieved / needs_user) and up to 2 new tasks. "Achieved" is only accepted when nothing is queued. needs_user pauses the goal with a question for you.

Task

One concrete unit with acceptance criteria and an optional shell check. Statuses: proposed, pending, active, done, failed, blocked. A task from a goal carries the goal's vision as context so the agent knows why it is working.

Why goals and ideas were empty: the only automatic producer was the daemon's idea cycle, which runs at most every 4 hours, only when completely idle, and nothing creates goals except promotion. Chat itself never created any of them. The new reflection pass fixes the chat side; goal creation is still deliberately a human decision.

The post-turn reflection is wired into the server, not exposed as a hook event. If you want to attach your own logic to it, it would need a reflect event added to the hook list.

9. Files, uploads and project folders

Project folders

A project is a directory (the folder picker can now choose any directory; / and the bare home folder are refused). The agent's file tools resolve every path inside that root and reject anything outside it. Cadence keeps its own per-project data in <project>/.cadence/ (project skills and plugins, attachments). Switching project switches the tool set, instructions, skills, sandbox and browser.

The file explorer

Backed by /api/files*, all confined to the project root. Raw files are served with a sandboxing CSP so an HTML file the agent wrote cannot call the API with your session. Edits check the file's modified time so you and the agent do not overwrite each other. When the agent writes a file you get a live "edited by the agent" marker.

Uploads to chat

  1. The file is first saved to an inbox with a random prefix (limit 50 MB, images have their own limit).
  2. When you send, non-image files are copied into <project>/.cadence/attachments/, so the agent can keep reading them with read_file.
  3. The text is extracted (PDF, Office, spreadsheets, archives and so on) and the first 15,000 characters are pasted into your message. Longer files say how to read the rest.
  4. Images go to the vision model on the message itself.

Canvas and browser

The canvas holds documents the agent writes (20 saved versions each; the agent re-reads before editing so it sees your changes). The browser is a real Chrome/Chromium driven through Playwright, one per project with a persistent profile under ~/.cadence/state/browser/, that you can watch and use too.

10. Findings and recommendations

Context window is probably set too low (highest impact). Neither your config nor settings define context_window for the big model, so Cadence assumes 32,768 tokens. Compaction starts at 70% of that (about 23k tokens) and compacts down to 40%. With a larger model you are summarising history much earlier than needed, and the compaction calls themselves cost minutes on a 35B model. Set the real window under Settings → Models.
Memory scoping: fixed. Each memory now records the project it was learned in. Recall, the agent's memory_search, the planner, brainstorming and reflection see that project's memories plus shared ones (project blank). Older memories load as shared. The Memory page defaults to "This project + shared", can show all projects, and new memories can be marked shared. Lessons consolidated by the daemon across several tasks are stored as shared.
The "small" model is the big model. Compaction, distillation, reflection and lesson consolidation all use small, which is set to the same 35B model. They are fine quality-wise, but each one queues on the same server and can delay your next chat message. A genuinely small model for these jobs would make them cheap.
Reflection can only see what the agent saw. It reads the last turn (cut to ~14k characters, tool results clipped to 400). It does not run after daemon tasks (those already write their own episodic and procedural memories). Ideas it files are goal-sized or task-sized suggestions, not active work.
The stop hook does not fire on interrupts or errors. It only runs when the model finishes normally. A hook that cleans up or logs per turn will miss stopped turns.
Daemon tasks do not draw documents live. Live canvas streaming is wired for chat turns. A task run by the daemon still shows its document only when the tool call completes.
Housekeeping. ~/.cadence/plugins/guard.py still says "Kestrel" in its docstring (cosmetic). The memory collection in your settings is still named kestrel_memory (works, just an old name). Nothing ever deletes or merges memories, and de-duplication is exact-text only, so reflection will slowly accumulate near-duplicates unless pruned from the Memory page.
Things that work well. Tool results are truncated and old ones shrunk before they eat the window; compaction never splits a tool call from its result; objective verify commands overrule the model's opinion of its own work; path confinement plus bwrap keep the agent inside the project; skills load progressively; and the repeated-call guard stops simple loops.

Update: goals, priorities, memory and Brainstorm

  • Root cause of empty ideas/plans/reflections: short max_tokens limits were consumed by the thinking model, leaving an empty answer. Structured calls now get reasoning_headroom (6000) extra tokens.
  • Goals: every goal has a priority (1-5) and is re-evaluated every goal_review_minutes (60) even with tasks queued; each plan leaves a prioritised, estimated, dated next task.
  • Priority: the daemon runs tasks by task priority + goal priority + user boost; while a chat turn is running only user or urgent tasks start. System-prompt sections carry weights and the lowest are trimmed first.
  • Memory: reflection files episodic, semantic and procedural memories after chat turns and daemon tasks; near-duplicates are folded.
  • Hooks: new events goal_planned, heartbeat, reflection.
